# ACC v0.12.1 release candidate evidence

This candidate ships the work merged to main after 0.12.0:

- ACC's Codex permission profile is available, not the default, and ACC's own Codex entries are recognised after a config rewrite removed their markers (#330, issue #329);
- the Codex 0.164.0 daemon, which runs with `--analytics-default-enabled`, is verified (#332, issue #331).

Both are fixes to the Codex integration; no new attention kind, CLI surface or captured minimum is added, so this release is a patch. Store contract 7 and managed-update protocol 2 are unchanged: between `v0.12.0` and this candidate, the protocol, core and storage packages change only their version field. This is candidate preparation, not publication.

### State continuity, with client detection shims

Setup:
- The archive was installed with isolated home, data, project and npm cache directories.
- Claude Code 2.1.259 and Codex 0.135.0 detection shims stood in for the clients.
- Both integrations were installed, and automatic updates were turned off.
- `acc update --yes` received the exact 0.12.1 archive from a local registry. Eleven checks passed.

- The updater activated 0.12.1. It downloaded the archive from the local registry, and the registry logged the request for the archive.
- The automatic-update opt-out set before the update survived it (`auto: false`).
- An MCP participant on the old 0.12.0 process held a question sent before the update.
  After the switch, that old process read the question with the same id and subject and
  answered it. The reply reached the sender.
- `.claude/settings.json` and `.codex/config.toml` kept their bytes.
- All 379 archive files were installed in the active generation with the same SHA-256.
- After the original npm installation was removed, the stable CLI reported 0.12.1. The
  stable read-only indicator answered (`ACC ! · acc doctor`).
- The local registry, MCP process and fixture directories were closed and removed.

The detection shims avoid native service preparation, so this proves package and state
continuity, not native activation.

### The Codex profile migration, with real Codex 0.164.0

This is the change the release exists for, so it ran on the real client. Setup:
- An isolated home and `CODEX_HOME` with a short path, so that Codex can bind its control socket.
- A data home outside the sandbox's writable paths.
- A trusted project.

Ten checks passed:
- Published 0.12.0, installed with `--delivery actionable`, selected
  `default_permissions = "acc-workspace"` for every chat. A `codex exec` chat (approval
  `on-request`, auto-review) ran in that profile, with network access enabled. It sent a
  message and took a claim through ACC's wrapper.
- `acc update --yes` on 0.12.0 took the exact 0.12.1 archive from a local registry and
  activated it.
- The refreshed integration selected `default_permissions = ":workspace"` inside ACC's
  block. It kept the `acc-workspace` profile defined and marked.
- Doctor reported that ACC's rules file runs its commands outside the Codex sandbox.
- A new `codex exec` chat ran in plain `workspace-write`. It sent a message and took a claim
  through the wrapper, and both were stored.
- `acc uninstall --adapter codex` restored the original `config.toml` byte for byte.
- The Codex service that the run started, and every isolated directory, were removed afterwards.

## Limits

- No new live capability, captured minimum or store contract is declared.
- Published source, artifact and native capture records remain unchanged.
- The rule bypass was captured on Codex 0.164.0 on macOS. ACC applies it from 0.164.0 onward on every platform with a rules file; Windows has none and keeps selecting ACC's profile.
- Codex Desktop was not driven. Its menu reads the same `default_permissions`.
- These checks do not establish native activation of the maintainer's running sessions, or native behavior on Windows and Linux. CI covers both platforms' suites.
- Publication remains a separate step after the release pull request merges.
