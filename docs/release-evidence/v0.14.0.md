# ACC v0.14.0 release candidate evidence

This candidate ships the work merged to main after 0.13.0, which is all from #400: Kimi Code
`Stop` continuation and Kimi Web wake-only live delivery (#390), Codex sender permissions that
follow Kimi's live policy, and a Windows fix for the status-line offer observation. It also
carries one update fix found by the review of this candidate: the managed refresh now writes
Codex's `127.0.0.1` rule in the same update that first activates Kimi Web.

The release adds a capability and keeps store contract 8, so it is a minor version with no data
migration. Managed-update protocol 2 is unchanged. This is candidate preparation, not
publication.

## Upgrade from published 0.13.0

The previous archive was downloaded from npm. Its SHA-256 matched the published 0.13.0 record:
`195d41811ea5a868a8e1aae6ae533e6f9310da045bdfd7a5e272708c912f02d6`.

Setup:
- isolated home, data home, npm prefix and npm cache under a resolved path;
- client detection shims for Claude Code 2.1.316 and Codex 0.166.0;
- a local registry that served the exact candidate as 0.14.0.

Fifteen checks passed:
- 0.13.0 installed both integrations, and the automatic-update opt-out was set.
- Two CLI participants attached. The sender recorded a question while the store was on
  contract 8.
- `acc update --yes` activated 0.14.0, the stable CLI reported 0.14.0, and the opt-out survived.
- After the update:
  - the peer saw the question and replied;
  - the sender received the reply;
  - the workspace's store identity still reported contract 8.
- `.claude/settings.json` and `.codex/config.toml` kept their bytes. With Kimi absent, the Codex
  profile gained no network rule.
- All 390 archive files were installed in the active generation with the same SHA-256.
- The stable CLI answered 0.14.0 after the npm installation was removed.

The detection shims avoid native service preparation, so these checks prove package and state
continuity, not native activation.

## Upgrade with Kimi recorded as actionable

This second upgrade follows the path an earlier explicit `acc install --delivery actionable`
leaves behind. Same isolation and local registry; shims for Codex 0.166.0 and Kimi Code 2.4.1.

Thirteen checks passed:
- 0.13.0 installed Codex with `--delivery actionable`, which writes ACC's Codex permission
  profile, and accepted `--delivery actionable` for Kimi. It recorded Kimi as `actionable`,
  from an explicit option, with no native activation. The Codex profile had no loopback rule.
- `acc update --yes` activated 0.14.0. The update activated Kimi live delivery as
  `actionable` from that record, and the same update wrote the exact `127.0.0.1` rule into the
  Codex profile. `acc doctor` reported no uncovered loopback receiver.
- `acc install --adapter kimi --delivery off` then removed the rule.

The same script against the candidate built before the refresh fix (`b0aad336`) failed two
checks: the Codex profile had no loopback rule after the update, and doctor reported the
uncovered receiver. The Codex shim has no daemon commands, so no Codex service was started.

## Real Kimi Code 2.4.1, installed from the exact archive

Every case ran the real `kimi` 2.4.1 client with an isolated `HOME`, `KIMI_CODE_HOME` and ACC
data home, installed hooks from the extracted archive, and a deterministic local provider on
`127.0.0.1`. The provider is a stub: it answers a request that names an ACC message with an
`acc reply` tool call. It does not establish a Moonshot model's judgment.

| Case | Result |
|---|---|
| Kimi Web idle wake, busy queue, reply, duplicate, fallback/restart, exact binding (C01-C06) | 6 of 6 passed; owned processes stopped and temporary state removed |
| Token rotation with a fresh binding | woken |
| Session created in manual mode | queued, no provider request |
| Session bound in `yolo`, then switched to manual | queued, no provider request |
| Foreign session lock | queued, no provider request |
| Reclaimed (cold) session | queued |
| `kimi -p`, a question arriving mid-turn, `Stop` continuation | the continuation carried ACC's notice and the message id, never the body; `acc reply` acknowledged the message |

The recorded C01-C06 run names this archive's SHA-256. The same scenarios on the reviewed
#400 head are in [the review evidence](kimi-delivery-review-2026-11-01.md).

## Limits

- Kimi Web delivery was captured only with a pre-existing loopback server on darwin-arm64 in
  `yolo` mode. The lock or lease check to prompt submit race remains, because Kimi has no
  conditional warm-only submit.
- No real Codex session sent to Kimi Web in these runs; the Codex permission changes are covered
  by the package's unit and command tests.
- Publication remains a separate step after the release pull request merges.
