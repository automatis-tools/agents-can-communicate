# ACC v0.9.0 release evidence

ACC runs natively on Windows, with live delivery to Claude Code, Codex and Antigravity CLI there.
Antigravity's desktop app gets live delivery through its own language server. An uninstall takes
back only what its own data home installed.

  merge of #254 and a documentation commit.
- Archive: `agents-can-communicate-0.9.0.tgz`, packed from that commit.
- Size: 554,498 bytes; 336 packed entries.
- SHA-256: `52cf072e91da74c072fade123ba94d4c6c03c72c1504de087ab8042a6159936f`.
- The root and fifteen bundled workspaces are at `0.9.0`. The Antigravity plugin manifest, the

`scripts/verify-package.mjs` passed on that exact file. It checked:

- every packed Markdown link resolves;
- the root and fifteen bundled workspaces are at 0.9.0;

## What changed since 0.8.5

Five merged pull requests changed the package. Their development records are below this
section of the CHANGELOG:

- **#235 (#234).** Native Windows: portable filesystem primitives for the store and the managed
  runtime, a Node shim in each client's own hook-shell form, the process table through WMI,
  state in `%LOCALAPPDATA%`, and `windows-latest` in the CI test and package matrices.
- **#243.** Live delivery on Windows: the Claude Code inbox pipe with the peer key, Codex through
  `codex app-server proxy`, and the Antigravity relay on a named pipe. A hook does less work on
  each turn: fewer flushes, no writer lock for an absent binding, and no journal completion
  marker. A real-clients CI job runs Claude Code and Codex on Linux and Windows.
- **#252.** The Antigravity install also allows the relay start command, so an unattended
  Antigravity CLI session starts its relay without a prompt.
- **#254 (#171).** The Antigravity desktop app as a client variant with its own evidence and live
  delivery through its language server; the running client's version and restart rebind; Codex
  app chats as `client_session_embedded`.
- **#255 (#253).** `acc uninstall` without `--adapter` skips a client that the current data home
  did not install.

Four more (#242, #244, #248, #249) changed only tests and their fixtures. A documentation
commit on the release branch corrects pages that still said native Windows keeps next-turn
delivery, Linux is uncaptured, and live delivery needs Apple Silicon macOS.

## Upgrade from the published 0.8.5

The published `agents-can-communicate@0.8.5` (sha256 `f593a339…`, as recorded for 0.8.5) was
set up as follows:

- installed from npm into an isolated prefix, with its own `HOME`, `ACC_DATA_HOME` and project,
  and a `PATH` that held only the prefix, the client stubs, node and system directories;
- wired to Claude Code and Codex through version stubs (`--delivery actionable`);
- given a local registry that served this exact archive.

Its own `acc update` printed `Updated ACC to 0.9.0; integrations refreshed.`. After the update:

- `version` answered `0.9.0`.
- The active generation was `0.9.0-e2129d7483704c4f70955edb`, beside
  `0.8.5-2e048e5495553522a5557872`.
- The runtime kept four launchers.
- Doctor reported `ACC 0.9.0 is active` and a healthy store.
- The Codex profile was byte for byte the one 0.8.5 wrote, with the same four socket grants.
- The installed generation matched the extracted archive file for file (`diff -r`).
- The registry saw three requests; the last was for the 0.9.0 tarball.

`reclaim.json` named the 0.9.0 generation with `complete: false` right after the update. After
an `acc status` from npm's `acc` and one from ACC's launcher, both generations stayed. With
`attemptedAt` moved two hours back, the next launcher `acc status` started the 0.9.0 worker. The
worker removed the 0.8.5 generation and recorded `complete: true`.

## Mixed versions

The published 0.8.5 code and the installed 0.9.0 shared one store. The 0.8.5 code ran from its
own package through its entrypoint. In that store:

- 0.9.0 sent a question to a participant that 0.8.5 had attached;
- 0.8.5 found the question in its inbox and replied;
- 0.9.0 received the answer;
- both reported `2 live`;
- 0.8.5 synced the full store (6 events, none repeated);
- both doctors reported the store healthy.

0.9.0 writes no journal completion marker, and 0.8.5 read and wrote that store. `STORE_VERSION`
stays 6.

## Real clients

On the maintainer's Mac (macOS arm64), the real-clients tests ran against this commit's packed
tree, with an isolated home and a model stub on 127.0.0.1:

- An idle interactive Claude Code 2.1.289 woke through its inbox socket when another session
  asked it a question, and the model read the message with no one typing.
- Claude Code 2.1.289 and Codex 0.160.0 attached through their own hooks, saw each other, and
  carried a message into the next turn.

The real-clients CI job runs the same two tests on `ubuntu-latest` and `windows-latest` for
every pull request; both passed on the final head of #254 (`9a23121f`).

Captured with real models during development, each in an isolated data home:

- **Antigravity 2.19.1, the desktop app** (#254, a private 0.8.99 build of that branch): an idle
  conversation woke, a push during a long answer waited for it, the woken agent answered with
  `acc reply` and no prompt, a resent message arrived once, a message to a quit app stayed
  queued, and after a restart the next turn bound the conversation again.
- **Antigravity CLI 1.2.16** (#252, a private 0.8.99 build): the agent started its relay with no
  approval prompt, and a question pushed into the idle session was answered with `acc reply`.
- **Claude Code 2.1.286 on Windows** (#243, `windows-latest`): the inbox pipe dropped a frame
  without the auth line and ran a turn after the peer key's auth line.
- **Codex 0.159.3 on Windows** (#243, `windows-latest`, under a standard user): a queued message
  reached the model through `codex app-server proxy`.
- **The uninstall change** (#255, the packed candidate, an isolated `HOME` with two data homes):
  an uninstall from the data home that had not installed left the other one's wiring
  unchanged; `--adapter` still removed it.

## Limits

- The Antigravity desktop app was captured on 2.19.1, darwin-arm64 only. Its Windows and Linux
  builds are uncaptured, and the bind needs `lsof`.
- Codex 0.160.0 ran only the next-turn check here. Its LocalDaemon live push was not captured
  again for this release; the latest records are 0.159.1 on macOS (0.8.5's evidence) and
  0.159.3 on Windows (#243).
- Codex live delivery on Windows needs a daemon started from a terminal that is not elevated.
  The CI Windows runner is elevated.
- The upgrade and mixed-version checks used version stubs for Claude Code and Codex.
- Linux and Windows were exercised only through CI.
