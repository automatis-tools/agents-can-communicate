# ACC v0.8.2 release evidence

Live delivery reaches every peer it was meant to on the maintainer's machine: a Codex session
wakes a Claude Code session, an Antigravity session woken while nobody is at its terminal
answers without an approval prompt, and doctor and status stop calling a working or idle
session broken. Two defects that were already in `main` are fixed on the way: detection ran the
client's version probe on the wrong PATH, and a store opening beside the stage sweep could fail
on Linux.

## What changed since 0.8.1

Four merged pull requests, each with its own development record below the 0.8.1 section of
the CHANGELOG:

- **#216, idle and working sessions reported as broken** (#209, #210, #215). Doctor re-verifies
  a lapsed delivery lease as the router does; status and doctor describe a stale session by what
  a message meets (`idle, wake on send`, `idle until next turn`, `idle, inbox only`); a turn
  spent in shell commands keeps the session online.
- **#218, ACC commands without an approval prompt in Antigravity CLI** (#214). Every install
  adds `command(<wrapper>)` to Antigravity CLI's `permissions.allow`, the skill calls the
  wrapper without quotes, and uninstall removes every copy of that rule.
- **#217, Codex sessions blocked from waking Claude Code** (#213). ACC's Codex permission
  profile also allows the Claude Code inbox directories, declared by the Claude Code adapter
  from its environment and from the inboxes ACC has bound; grants are written in resolved
  form; doctor reports configured only when every receiver socket is granted. Found on the way
  and fixed here: the version probe ignored the PATH detection was given, and a store opening
  beside the stage sweep failed with ENOENT on Linux (11 of 4,000 eight-way first opens in a
  `node:24-bookworm` container before, 0 of 4,000 after).
- **#219, a first doctor in a new project** stops printing `history from undefined`.

## Real clients on the maintainer's machine

On 2026-09-27, with 0.8.1 installed, a question sent to each idle peer measured the gaps this
release closes: Claude Code (2.1.283) and Codex (0.157.1), both called `degraded` by doctor,
answered within 12 seconds; a Codex session's reply to Claude Code printed "live offer blocked
by sender permissions"; Antigravity CLI (1.2.12) took the push and stopped at an approval prompt
for its first ACC command.

On 2026-09-28 a local build of #217 and #218 over `main` (version set to `0.8.99` only, sha256
`ea2f81eb063548246615fe78685f6787748cd3149cfef12d65efb82f6e2ca37e`), installed into an isolated
prefix and data home, with the real client homes backed up and restored byte for byte, ran with
new TUI sessions of all three clients:

- a Codex session's `acc message` to a Claude Code session idle for 18 minutes printed
  `woke claude_code-46c2Qj via claude-inbox`; the woken turn showed Claude Code the question
  0.6 s after the send, its answer was recorded 11.6 s after the send, and the answer reached
  Codex live through `codex-app-server`;
- an Antigravity session woken by the relay with nobody at its terminal ran
  `<wrapper> status …` and `<wrapper> reply …` with no approval prompt and answered six seconds
  after the send; a question from the Codex session was offered live and answered the same way;
- `acc uninstall --adapter antigravity` returned the settings file to its pre-install bytes.

That build predates the review fixes on #217 and #218 (every inbox record read, every copy of
the rule removed, a reinstall claiming only what it creates, the stage-sweep race). Those are
covered by tests on macOS and Linux, not by a real-client run of this exact archive.

## Upgrade from the published 0.8.1

The published `agents-can-communicate@0.8.1` was installed from npm into an isolated prefix
with its own `HOME`, `ACC_DATA_HOME` and project, wired to Claude Code and Codex through version
stubs (`--delivery actionable`), and given a local registry serving this exact archive. Its own
`acc update` printed `Updated ACC to 0.8.2; integrations refreshed.`: `version` answered
`0.8.2`, the active generation was `0.8.2-b44fb970407188c0a0d41009` beside the kept
`0.8.1-96fb9971ce832cb8e83842a0`, the runtime kept four launchers, both install records kept
`actionable` and their decisions, and the Claude Code plugin cache held `0.8.1` and `0.8.2`.
The Codex profile 0.8.1 wrote (`/tmp/acc-ch-501` and the control socket) was rewritten by the
refresh to `/private/tmp/acc-ch-501`, the control socket, `/private/tmp/cc-socks` and
`/private/tmp/cc-socks-501`, and doctor reported Codex outgoing delivery configured. The
registry saw three requests, the last for the 0.8.2 tarball.

## Mixed versions

The published 0.8.1 code, run from its own package through its entrypoint, and the installed
0.8.2 shared one store: 0.8.2 sent a question to a participant 0.8.1 had attached, 0.8.1 found
it in its inbox and replied, 0.8.2 received the answer, both reported `3 live`, and 0.8.1 synced
the full store (7 events). `STORE_VERSION` stays 6; the new status fields are computed at read
time.

## Compatibility notes

- `acc update` rewrites an ACC-owned Codex profile under any recorded policy, `off` included,
  so it grants the Claude Code inboxes; a profile the user edited stays theirs and doctor names
  the missing grants. Start a new Codex session after the update.
- Every Antigravity CLI install writes `command(<wrapper>)` into
  `~/.gemini/antigravity-cli/settings.json`; restart `agy` to load it. A wrapper path that needs
  quotes gets no rule, and doctor says why.
- Status rows gain `processTracked`, `liveDelivery` and `liveLeaseCurrent`.

## Limits

Linux Codex sandboxes, `XDG_RUNTIME_DIR` inboxes and Termux paths are covered by tests with an
injected platform only. A Claude Code session in a new inbox directory is granted after the next
install or update. This release does not change Grok; its re-capture is #159. Open questions:
#211 (attention for a wakeable recipient) and #212 (Codex presence follows the app-server
daemon). Antigravity print mode with the rule was not captured.
