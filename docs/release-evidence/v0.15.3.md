# ACC v0.15.3 release candidate evidence

This candidate ships the work merged to main after 0.15.2: #428, which makes `acc doctor` ask the
running Codex service which of ACC's hooks it would run, instead of asking for a review on every
run.

The release keeps store contract 8 and managed-update protocol 2, so it is a patch version with
no data migration. This is candidate preparation, not publication.

## Exact artifact

- Source: clean commit `8ee41cd71615881b4ac72ed5ec0e342cb727c83b`, on main `3a81a1bf` (PR #428).
- Archive: `agents-can-communicate-0.15.3.tgz`, 661,655 bytes, 392 files.
- SHA-256: `7e582bc6350e104a750cf58d783eaaa8142639fff0639947afd4e49ebb568fc6`.
- SHA-1: `97928ce74b34d2a14fc9f807210433a9b0d1a80e`.
- Node 24.4.0, npm 11.4.2, macOS arm64.
- The root manifest, fifteen workspaces and two versioned embedded manifests declare 0.15.3. So
  does the lockfile. The two Codex plugin manifests carry no version in source; ACC stamps them
  at install.
- `npm ci` with a release-only cache and the syntax check of 924 modules passed before commit A.
- The documentation-reader audit pin was refreshed after commit A. The external reader list is
  unchanged: the new test file reads only its own package's fixture.

The exact archive passed `scripts/verify-package.mjs`, which checks:
- bundled workspaces, the certification inventory and packed links;
- all four binaries, doctor and a non-Git workspace;
- client-home restoration after install and uninstall.

Source packed from the candidate commit passed all 25 managed-update checks in
`tests/acceptance/managed-*-packed.test.mjs`.

## Upgrade from published 0.15.2

The previous archive was downloaded from npm. Its SHA-256 matched the published 0.15.2 record:
`9e3957955fe174cb8e4704b3450f79603c78332461654295fe56c88c0de4633f`.

Setup:
- isolated home, data home, npm prefix and npm cache;
- real client executables on `PATH` through a symlink-only directory: Claude Code 2.1.330 and
  Codex 0.171.0;
- a local registry that served the exact candidate as 0.15.3, and then the same archive
  re-versioned as 0.15.4;
- a closed local port standing in for an unreachable registry.

Under 0.15.2, Claude Code was installed with no `--delivery` and Codex with `--delivery off`.
Twenty-four checks passed:
- 0.15.2 installed both integrations, with the hooks in `agents-can-communicate-hooks`, and its
  doctor asked for the hook review.
- `acc update --yes` activated 0.15.3 with the notice "ACC 0.15.3 is active."
- The hooks plugin kept its 0.15.2 copy with the same content hash, by a port of Codex's
  `plugin_fingerprint.rs`. The skill plugin moved to 0.15.3 beside its 0.15.2 copy. ACC's block
  in `config.toml` still enables the hooks plugin.
- Claude Code's `settings.json` kept its bytes.
- With no Codex service in that home, 0.15.3's doctor reported hook readiness as unverified. It
  started no Codex process and left `config.toml` byte for byte.
- A question recorded under 0.15.2 crossed the update. The peer saw it and replied, the sender
  received the reply, and the store stayed on contract 8.
- All 392 archive files were installed in the active generation with the same SHA-256.
- 0.15.3's update worker, run against the closed port with a due check, named the cause
  `fetch failed (ECONNREFUSED)`. The next due pass against the local registry cleared it.
- The update to 0.15.4 left the hooks plugin on its 0.15.2 copy with the same hash.
- The stable CLI answered 0.15.4 after the npm installation was removed.

## Real clients

On 2026-11-22 the candidate's packed Codex adapter ran its detection read-only against the
maintainer's home and running Codex 0.171.0 service, with the process and socket checks of chat
discovery. In 197 ms it reported "Codex reports ACC's hooks enabled and trusted: sessionStart,
userPromptSubmit, preToolUse, stop, sessionEnd" and asked for no hook review. The modification
time of `~/.codex/config.toml` stayed the same, and the number of Codex app-server processes did
not change.

The candidate differs from 0.15.2 by `packages/adapter-codex/src/{adapter,install,native-discovery}.mjs`
and their tests, by version numbers, by the `docs/UPGRADING.md` section and by the
documentation-reader pin. The changed code runs in doctor and in Codex chat discovery.

## Limits

- No Codex session was opened in the upgrade check, so it proves the files Codex trusts, not the
  trust dialog itself.
- A Codex service that runs only some of ACC's hooks was exercised in tests, not on a real
  client.
- Linux and Windows ran in CI only.
