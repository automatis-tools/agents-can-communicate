# ACC v0.8.3 release evidence

`acc update` right after a release installs the release that discovery found. Before this
release, npm could answer the download from a package document it had cached before the
registry listed the release, and the update failed with `ETARGET`.

## Exact artifact

- Source: clean commit `3dcd155d685b167770f7bf79c23d282ada663809`. It is the version sweep
  `34eacc0` plus two test-only commits (see "CI on the release pull request").
- Archive: `agents-can-communicate-0.8.3.tgz`, packed from `34eacc0` and packed again from
  `3dcd155`; the two archives are byte-identical, because npm packs no test file.
- Size: 486,699 bytes; 315 packed entries.
- SHA-256: `6047fba45684018f89af81e3397a9f4745a2395d39018aa189fbd6e0175127d6`.
- Root and fifteen bundled workspaces at `0.8.3`; the Antigravity plugin and Gemini
  extension manifests and the lockfile carry the same version sweep as 0.8.2, over the same
  nineteen files. `docs/UPGRADING.md` tells a 0.8.2 or older install how to update when npm
  answers `ETARGET`.

`scripts/verify-package.mjs` on that exact file: 315 entries with none forbidden, six
certification manifests, every packed Markdown link resolving, root and fifteen bundled
workspaces at 0.8.3, `acc`, `acc-hook` and `acc-mcp` present, doctor reporting six adapters, a
workspace with no Git writing nothing into the project, and client install/uninstall restoring
topology, modes, links and bytes, with a repeated uninstall a no-op.

All 24 managed-update packed checks passed against real installed archives, including the new
check for a release that npm's cache does not list yet.

## What changed since 0.8.2

One merged pull request, with its development record below the 0.8.2 section of the
CHANGELOG:

- **#222, an update right after a release** (#221). The download runs `npm install
  --prefer-online`, so npm revalidates cached package documents with the registry. The
  downloaded archive is still checked against the integrity that discovery returned.

## The defect on the maintainer's machine

On 2026-09-28, `acc update` from 0.8.1 to the just-published 0.8.2 failed with `ETARGET`.
The registry listed 0.8.2 at 22:24:47Z. npm had cached the package document without it at
22:22:54Z with `max-age=300`. The update at 22:25:57Z logged `cache hit`. The same update with
`npm_config_prefer_online=true` at 22:27:18Z, while that cache entry was still fresh, logged
`cache updated` and activated 0.8.2. This release makes that setting part of the download.

## Upgrade from the published 0.8.2

The published `agents-can-communicate@0.8.2` was installed from npm into an isolated prefix
with its own `HOME`, `ACC_DATA_HOME` and project, wired to Claude Code and Codex through version
stubs (`--delivery actionable`), and given a local registry serving this exact archive. Its own
`acc update` printed `Updated ACC to 0.8.3; integrations refreshed.`: `version` answered
`0.8.3`, the active generation was `0.8.3-ed06e6f8519ec18da9323742` beside the kept
`0.8.2-b44fb970407188c0a0d41009`, the runtime kept four launchers, and doctor reported
`ACC 0.8.3 is active` with Codex outgoing delivery configured. The Codex profile kept the same
four grants. The installed generation matched the extracted archive file for file
(`diff -r`). The registry saw three requests, the last for the 0.8.3 tarball.

## CI on the release pull request

The first CI run on #223 failed one test on each platform. The failing tests were outside this
release's change, and both failures came from races in the test harness:

- **ubuntu:** `inbox-delivery.test.mjs`, "a wake that failed to write does not stop a later
  one", read no wake (`0 !== 1`). Four tests raced a wake they expected against a 150 ms timer
  that started before the offer. Under load the offer alone took up to 114 ms. In
  `node:24-bookworm` on one CPU with two CPU-bound processes and eight parallel copies, the
  file failed in 29 of 120 runs. The tests now wait for the connection to close, with a 5 s
  limit that only turns a missing wake into a failure. With this change the same load gave 0 of
  120 failures. With the wake marker kept after a failed write, the test still fails.
- **macOS:** `managed-runtime-retired-kinds.test.mjs`, "an old shim reaching the bootstrap stub
  runs the vendor command unchanged", failed with an unhandled `write EPIPE` on the child's
  stdin. The bootstrap stub never reads its input, so the harness's write can meet a closed
  pipe. It was not reproduced in 800 macOS and 160 Linux runs under load. The harness now
  ignores EPIPE only, and any other stdin error still fails the test.

Both changes are test-only commits (`5888bdf`, `3dcd155`). The candidate-record gate watches
all of `packages/`, test directories included, so the record moved to `3dcd155`. The archive
packed from it matched the verified one byte for byte.

## Compatibility notes

- The update to 0.8.3 is downloaded by the installed version. An install on 0.8.2 or older can
  still meet `ETARGET` right after this release; `npm_config_prefer_online=true acc update`
  avoids it, as `UPGRADING.md` says. Updates performed by 0.8.3 and later need no setting.
- No store, hook, client-integration or status change.

## Limits

No real-client session was run for this release: nothing a client runs changed. The fix was
measured on the maintainer's machine through the equivalent npm setting and by the packed
check, not by an update performed by the released 0.8.3 itself.
