notice directly. After an update, the previous runtime generation is removed an hour later, with
automatic updates on or off.

## What changed since 0.8.4

Two merged pull requests. Their development records are below the 0.8.4 section of the
CHANGELOG:

- **#231 (#230).** The Codex adapter names the first launch option on an embedded chat's
  command line that keeps it embedded. The option travels with the refusal as `launchOption`,
  and the native-attempt record keeps it. The chat's notice, doctor's session line and the
  sender's line (`nativeLaunchOption`) advise starting Codex without the option. On its one
  turn, the notice is printed as the hook's `systemMessage`, which Codex shows the user and never
  sends to the model. This was measured on Codex 0.147.0, 0.155.1 and 0.159.1, and on a real
  0.159.1 `codex --search` chat with the candidate installed.
- **#232.** An `acc update` runs from the generation it replaces and holds a lease on it. Its
  in-process reclaim therefore keeps that generation, but it used to record the pass as done.
  The pass is now recorded as unfinished, and the hourly retry removes the old generation. This
  was found in this release's first upgrade preflight: there, the published 0.8.4 left its own
  generation in place with `complete: true`.

## Upgrade from the published 0.8.4

The published `agents-can-communicate@0.8.4` was set up as follows:

- installed from npm into an isolated prefix with its own `HOME`, `ACC_DATA_HOME` and project;
- wired to Claude Code and Codex through version stubs (`--delivery actionable`);
- given a local registry that served this exact archive.

Its own `acc update` printed `Updated ACC to 0.8.5; integrations refreshed.`. After the update:

- `version` answered `0.8.5`.
- The active generation was `0.8.5-2e048e5495553522a5557872`, beside
  `0.8.4-64eb6d4ee24c36031b6c44eb`.
- The runtime kept four launchers.
- Doctor reported `ACC 0.8.5 is active`.
- The Codex profile kept the same four grants.
- The installed generation matched the extracted archive file for file (`diff -r`).
- The registry saw three requests; the last was for the 0.8.5 tarball.

`reclaim.json` named the 0.8.5 generation with `complete: false` right after the update. It still
did after an `acc status` from npm's `acc` and one from ACC's launcher. Neither command started a
worker, and both generations stayed. With `attemptedAt` moved two hours back, the next launcher
`acc status` started the 0.8.5 worker. The worker removed the 0.8.4 generation and recorded
`complete: true`.

## Real clients

with the #231 candidate installed from its archive. Its record is in

The published 0.8.4 ran on the maintainer's machine the same day, with Codex 0.159.1:

- An empty daemon chat was registered and answered a request with its first turn.
- A closed TUI's session closed 60.4 seconds after the exit.

  moved to the new daemon's pid within 4 seconds.

## Limits

- The display of a hook's `systemMessage` was measured on Codex 0.147.0, 0.155.1 and 0.159.1
  only. Every Codex release from 0.144.1 to 0.159.1 accepts the field.
- A chat that is embedded because of an environment variable (`CODEX_EXEC_SERVER_URL`) or a
  configuration loader shows nothing on its command line, so it keeps the advice for a missing
  daemon.
- The old generation stays for an hour after an update and is removed by the first ACC command
  after that hour.
- Linux was exercised only through the CI suite.
