A native binding whose pid another program now has no longer holds a store-contract update, and
a pending release that cannot activate gives way to a newer one.

  merge of #278.
- Archive: `agents-can-communicate-0.10.2.tgz`, packed from that commit.
- Size: 580,985 bytes; 351 packed entries.
- SHA-256: `6e3d63508379246a971947ccd66c5e544e8a53932f4f95e9f179e85b40fa4ceb`.
- The root and fifteen bundled workspaces are at `0.10.2`. The Antigravity plugin manifest, the

`scripts/verify-package.mjs` passed on that exact file: 351 entries, none forbidden; six

## What changed since 0.10.1

One merged pull request changed the package; its development record is below this section of
the CHANGELOG:

- **#278 (#276, #277).** A binding whose live pid belongs to a process that started more than a
  second after the binding was last written is no hold (`ps -o lstart=` with `LC_ALL=C`, or WMI
  on Windows; an unreadable start time decides nothing), and the pending generation's refresh
  removes it. When the pending release reports `processes_active`, `acc update`, and the
  automatic update once a check is due, stage a newer release in its place; with nothing newer,
  the result still reports `processes_active`.

## Upgrade from the published 0.9.1

The published `agents-can-communicate@0.9.1` was installed from npm into an isolated prefix,
with its own `HOME`, `ACC_DATA_HOME` and project, a `PATH` of the prefix, client stubs, node and
system directories, and a local registry that served this exact archive:

- **A live 0.9.1 process.** 0.9.1's own `acc-mcp` held contract 6, and `acc update` waited for
  it. After it exited, the next `acc status` activated 0.10.2. The store was on contract 7 within
  0.8 seconds, with event, journal, message and receipt bytes unchanged, and 0.10.2 answered the
  open question on it. The installed generation matched the archive file for file, and the Codex
  `config.toml` was unchanged. 0.9.1 code refused the migrated store with exit 4.
- **Stale bindings.** Two bindings without a pid for sessions with no record: the 0.9.1 updater
  activated 0.10.2 after its refresh removed them, and the store moved to contract 7. With a
  third binding for a session that still heartbeats, that one stayed and kept 0.10.2 pending.
- **A reused pid.** A binding written two days earlier, whose pid now belonged to a `sleep`
  started at the time of the run: the 0.9.1 updater activated 0.10.2, the binding was removed,
  and the store moved to contract 7.
- **A stuck pending 0.10.1, as on the maintainer's machine.** With 0.9.1's `acc-mcp` holding
  contract 6, `acc update` staged the published 0.10.1. Offered 0.10.2, the 0.10.1 updater only
  retried 0.10.1. `acc update --pin none` cleared it, and `acc update` staged 0.10.2. Once the
  server exited, 0.10.2 activated, and only its generation remained.

## Limits

- The maintainer's own machine is updated after publication; that result is not part of this
  record.
- A machine with a pending 0.10.0 or 0.10.1 needs `acc update --pin none` once: their updater
  runs the decision and does not replace a pending release.
- Linux and Windows were exercised only through CI; the Windows start-time reading is covered by
  the unit test that reads the test process's own start time.
