# ACC v0.10.0 release evidence

Stores move to contract 7, which reads a bounded index on every send, and ACC migrates each
workspace's store by itself after the update. On Windows, a writer waiting for the store lock
looks again when the lock's record is being deleted. The README and docs lead with messages
between different vendors' clients.

## What changed since 0.9.1

Three merged pull requests changed the package. Their development records are below this
section of the CHANGELOG:

- **#263 (#241).** Store contract 7: a send and its retries read a rebuildable, bounded message
  and receipt index instead of rereading unrelated records. `acc doctor --migrate-store` moves a
  contract-6 store; hooks fail open on one and never change its format.
- **#264.** The activated generation migrates every contract-6 store of its data home itself,
  once no live process holds contract 6, and records `store-upgrade.json`; the launcher's
  scheduler retries an incomplete pass after a minute. Claude Code and Codex hooks print a
  `systemMessage` while a store waits, and plain `acc doctor` names the migration command.
- **#269.** On Windows, a writer's lstat of a name inside a lock directory that another writer
  is deleting answers EPERM; it is now asked again within the writer's deadline, and an open
  refused while the lock changed hands opens the new record. The change applies on Windows
  only.

#265, #266 and #268 changed only tests, the test runner and CI.

The release branch also rewrote the public texts for the position between vendors
(design: `docs/design/2026-10-06-cross-vendor-positioning.md`): the README, `docs/WHY_ACC.md`,
the openings of `docs/index.md` and `docs/GETTING_STARTED.md`, and the package description and
keywords. Gemini CLI left the README's client list and the keywords; its adapter is unchanged.

## Upgrade from the published 0.9.1

The published `agents-can-communicate@0.9.1` (sha256 `517023ba…`, as recorded for 0.9.1) was
set up as follows:

- installed from npm into an isolated prefix, with its own `HOME`, `ACC_DATA_HOME` and project,
  and a `PATH` that held only the prefix, the client stubs, node and system directories;
- wired to Claude Code and Codex through version stubs (`--delivery actionable`), which left
  automatic updates on;
- given a contract-6 store by its own commands: two attached participants, a question with its
  answer, and a second question left open;
- given a live 0.9.1 process holding contract 6: its own `acc-mcp` server, started through the
  launcher, whose runtime lease named `0.9.1` and store contract 6;
- given a local registry that served this exact archive.

Its own `acc update` printed `ACC 0.10.0 is ready; waiting for 1 active or unidentified
process(es): PID 12416 (acc-mcp; store contract 6).` and `acc doctor` printed the same notice.
`version` still answered `0.9.1`, both generations were present, and the store stayed on
contract 6.

The MCP server was then stopped. The next plain `acc status`, with updates allowed, started the
0.9.1 worker, which activated 0.10.0; 0.10.0 migrated the store. Within 2.5 seconds of that
command, while the packed checks ran beside it:

- `control.json` named `0.10.0` active, with no pending update;
- the store's `protocol.json` named `storeVersion: 7`, with the same workspace id and
  initialization time;
- `store-upgrade.json` recorded `complete: true`, `pending: 0`;
- `reclaim.json` recorded `complete: true`, and the 0.9.1 generation was gone.

A recursive comparison with the store copied before the update found only `protocol.json`
changed, a new `indexes/` directory, and eight new `stage/*.published` markers: every event,
journal, message and receipt file was byte for byte the same.

On the migrated store, 0.10.0 showed the open question in the recipient's inbox, recorded its
answer, and showed both answers in the sender's inbox. Doctor reported a healthy store,
`ACC 0.10.0 is active.`, and two of six adapters installed. The installed generation matched
the extracted archive file for file (`diff -r`). The Codex `config.toml` was byte for byte the
one 0.9.1 wrote. The registry saw three requests; the last was for the 0.10.0 tarball.

## Mixed versions

0.9.x code cannot open a contract-7 store. The published 0.9.1 code, run from its own package
through its entrypoint, answered `acc status` on the migrated store with exit 4 and
`unknown store version`. A 0.9.1 process that still runs, such as the MCP server above, holds
contract 6 and so blocks the activation; both versions never use one store.

## Real clients

On the maintainer's Mac (macOS arm64), the real-clients tests ran against the candidate commit's
packed tree, with an isolated home and a model stub on 127.0.0.1. Claude Code 2.1.291 and
Codex 0.160.1 attached through their own hooks, saw each other and carried a message into the
next turn, and an idle interactive Claude Code woke through its inbox. Both passed on the first
run, as they did on the earlier candidate.

The real-clients CI job runs the same two tests on `ubuntu-latest` and `windows-latest` for every
pull request; both passed on the final heads of #263, #264 and #269. On #264, Claude Code
2.1.289 showed the notice in its terminal, and Codex 0.160.1 (`codex exec`, which prints no
`systemMessage`) completed both hooks with it (see its development record).

moved within 1.7 seconds of the holder's exit), the mixed-version check, both real-clients

The archive packed from `a9edc13` (576,895 bytes, sha256 `a64974be…`) passed the package
verification, the same upgrade from the published 0.9.1 (the store moved within 2 seconds of
the holder's exit), the mixed-version check and both real-clients tests.

In its first packed run, the 24 managed-update checks and the explicit-migration check passed.
Two store-migration checks failed: they offered the update as `0.9.99`, which is no longer
newer than the installed `0.10.0`, so the update found nothing to stage. The test-only commit
`d9ff788` makes them offer the next patch above the installed version, as every other packed
update check does; the three store-migration checks then passed.

`npm test` on its evidence commit `56407f0` ran under `env -i` with only `HOME`, `USER`, `TMPDIR`,
a PATH of system directories plus node, and the release npm cache, as in CI. It gave 3,167
tests: 3,158 passing, 1 failing, 8 skipped, in 6.6 minutes, and left no test directory behind.

The failing test was `an installed hook preserves a prior backlog with client 99.0.0`. It took
43 seconds, against 6 to 7 alone, and its first turn carried no body of the fresh request. The
same file's 2.1.233 case passed. What was done about it:

- A second full run on the same commit, with four copies of this test repeated beside it for
  its whole length, gave 3,167 tests: 3,159 passing, 0 failing, 8 skipped, in 10.8 minutes. All
  84 copies passed.
- These variants also passed, with the body present in every run: 16 copies at once, 8 copies
  beside 36 busy processes, 8 beside 24 disk-flush writers, and 8 run as descendants of a live
  Claude Code process, as the suite is. One more ran with a client version probe slower than
  its one-second bound: the session recorded no client version, and the body still came.
- One input reproduces the exact failure: a SessionStart that did not attach the reader. The
  first turn then opens another participant, whose context carries only the owner line. The
  fixture's start helper ignored the hook's stderr, so the failed run cannot show whether its
  start failed open.
- The test-only commit `e2f5f05` makes this test run its SessionStart itself, require empty
  stderr, and print the turn's context when the body is missing, so a repeat names its cause.

The cause of the one failure is not known. Five skipped tests exercise Windows only (named
pipes, `.cmd` clients, WMI). Two are the real-clients tests, which need the clients on `PATH`;
they ran separately (see Real clients). One needs Gemini CLI absent from the machine.

## Limits

- The holder in the upgrade preflight was 0.9.1's own MCP server. No interactive client
  session started under 0.9.1 held the store there; a native binding is covered by the packed
  check `packed verified pending management code migrates only after old native holds exit`
  and by the #264 measurement on a copy of the maintainer's 42 stores.
- The preflight ran with automatic updates on. It did not exercise a pending 0.10.0 with
  automatic updates off after its holders exit.
- Linux and Windows were exercised only through CI.
