# ACC v0.8.4 release evidence

A new Codex chat is addressable before anyone types in it, a Codex chat that runs without the
app-server daemon says so, a new `CODEX_HOME` needs no standalone download, and a fix to the
reclaim of old runtime generations takes effect on the release that ships it.

## Exact artifact

- Source: clean commit `fe25de3d81b4e552617a6c1cd3bda67061aae1ff`. It is the version sweep
  `a3c01bd` plus one correction to `docs/UPGRADING.md` (see "Upgrade from the published 0.8.3").
- Archive: `agents-can-communicate-0.8.4.tgz`, packed from that commit.
- Size: 496,214 bytes; 318 packed entries.
- SHA-256: `04d1a12dbef2434497f434e319dfe5bf90d9d89c9d63c3d2b8ec0fc2bcca2f10`.
- Root and fifteen bundled workspaces at `0.8.4`; the Antigravity plugin and Gemini extension
  manifests and the lockfile carry the same version sweep as 0.8.3, over the same nineteen
  files. `docs/UPGRADING.md` describes what 0.8.4 changes around Codex and the one reclaim pass
  after the update from 0.8.3.

`scripts/verify-package.mjs` on that exact file: 318 entries with none forbidden, six
certification manifests, every packed Markdown link resolving, root and fifteen bundled
workspaces at 0.8.4, `acc`, `acc-hook` and `acc-mcp` present, doctor reporting six adapters, a
workspace with no Git writing nothing into the project, and client install/uninstall restoring
topology, modes, links and bytes, with a repeated uninstall a no-op.

All 24 managed-update packed checks passed against real installed archives.

## What changed since 0.8.3

Four merged pull requests, with their development records below the 0.8.3 section of the
CHANGELOG:

- **#225** (#224): a Codex chat that runs embedded reports `client_session_embedded`; the chat
  is told once, a sender sees the cause, doctor names it on the session line, and doctor's
  advice follows `daemon_auto_start`.
- **#226** (#212): documentation. A closed TUI (Ctrl-C or `kill -9`) closes its ACC session about
  60 seconds later, when the daemon unloads the thread and runs `SessionEnd`.
- **#227** (#167): status, doctor and MCP `acc_status` register idle Codex chats that the daemon
  holds, where ACC's hooks are enabled and trusted, before their first turn.
- **#228** (#205, #208): the self-installed daemon layout (`packages/app-server-daemon`,
  `daemon.pid`) is resolved for setup, maintenance and discovery; the activated generation's
  own reclaim runs after an activation and after an install, and its worker covers an update
  from an older release.

## Upgrade from the published 0.8.3

The published `agents-can-communicate@0.8.3` was installed from npm into an isolated prefix with
its own `HOME`, `ACC_DATA_HOME` and project, wired to Claude Code and Codex through version stubs
(`--delivery actionable`), and given a local registry serving this exact archive. Its own
`acc update` printed `Updated ACC to 0.8.4; integrations refreshed.`: `version` answered
`0.8.4`, the active generation was `0.8.4-64eb6d4ee24c36031b6c44eb` beside
`0.8.3-ed06e6f8519ec18da9323742`, the runtime kept four launchers, and doctor reported
`ACC 0.8.4 is active`. The Codex profile kept the same four grants. The installed generation
matched the extracted archive file for file (`diff -r`). The registry saw three requests, the
last for the 0.8.4 tarball.

The reclaim pass (#208), checked on the first candidate `a3c01bd`, did not start from the
npm-installed `acc status`: that command runs the entry of the version npm installed, 0.8.3,
whose scheduler does not know the pass. Run through ACC's own launcher, as client hooks and the
agent wrapper run it, the same `acc status` started the 0.8.4 worker, which wrote
`reclaim.json` naming the 0.8.4 generation with `complete: true` and removed the 0.8.3
generation. `docs/UPGRADING.md` said "the first ACC command"; commit `fe25de3` says the first
client hook or agent command, and the candidate was packed and verified again. On this final
candidate the same sequence gave the same results: no marker after the npm-installed command,
the marker and a single `0.8.4-64eb6d4ee24c36031b6c44eb` generation after the launcher.

## Mixed versions

The published 0.8.3 code, run from its own package through its entrypoint, and the installed
0.8.4 shared one store: 0.8.4 sent a question to a participant 0.8.3 had attached, 0.8.3 found it
in its inbox and replied, 0.8.4 received the answer, both reported the same live count, and 0.8.3
synced the full store (7 events). `STORE_VERSION` stays 6. The reply's live offer reported
`ambiguous_recipient_sessions` because the recipient had attached twice, once in a first run
of the check whose old-version runner passed no command; that run recorded nothing else.

## Real clients

These were captured during development, against real clients on macOS arm64, and are recorded
in each pull request's evidence:

- **Codex 0.158.0, #167:** a new TUI with nothing typed was registered by status; a request from
  a Claude Code session was offered through `codex-app-server` and answered `OK` by the chat's
  first turn from the registered session, and Ctrl-C closed it 61 seconds later.
- **Codex 0.158.0, #212:** Ctrl-C, `kill -9` and a TUI with no turn each closed through
  `SessionEnd` about 60 seconds after the exit.
- **Codex 0.158.0, #224:** a `codex --no-daemon` TUI was identified as embedded by the real
  handshake, and a daemon-hosted thread kept its own reason; a TUI opened with no daemon running
  started the daemon itself.
- **Codex 0.159.0, #205:** a daemon a fresh `CODEX_HOME` installed for itself was proven and
  inspected `ready`, and a second fresh home was prepared by setup and verified `ready`.

## Limits

- The embedded chat's notice reaching the model in a real `codex --no-daemon` chat was not
  captured; it is part of the maintainer's end-to-end check of this candidate.
- An `acc` installed globally by npm does not start the post-update reclaim pass; client hooks
  and the agent wrapper do.
- Linux was exercised only through the CI suite.
