# ACC v0.10.3 release evidence

A process that has exited but that its parent has not collected no longer holds an update, and
doctor no longer reports a maintenance failure that its release outlived.

## Exact artifact

- Source: clean commit `d1f1a5bc788a76d8f586415ce5ec598e025a4638`, the version sweep on the
  merge of #282.
- Archive: `agents-can-communicate-0.10.3.tgz`, packed from that commit.
- Size: 582,379 bytes; 351 packed entries.
- SHA-256: `94bff1849b8abd642d576fa0f5c71806d2012108c3ccac43a5119b82acc1025f`.
- The root and fifteen bundled workspaces are at `0.10.3`. The Antigravity plugin manifest, the
  Gemini extension manifest and the lockfile carry the same version sweep as 0.10.2, over the
  same nineteen files. `docs/UPGRADING.md` already describes 0.10.3, from #282.

`scripts/verify-package.mjs` passed on that exact file: 351 entries, none forbidden; six
certification manifests with the exact evidence allowlist; every packed Markdown link resolves;
the root and fifteen bundled workspaces at 0.10.3; `acc`, `acc-hook` and `acc-mcp` present;
doctor reports six adapters; nothing written into a project without Git; client install and
uninstall restore topology, modes, links and bytes, and a repeated uninstall is a no-op.

All 27 packed checks passed against real installed archives: the 24 managed-update checks and
the 3 store-migration checks.

## What changed since 0.10.2

One merged pull request changed the package; its development record is below this section of
the CHANGELOG:

- **#282 (#280, #281).** `processIsZombie` reads `ps -o stat=` with `LC_ALL=C`; a state that
  starts with `Z` is a zombie, and an unreadable state decides nothing. A native binding, the
  pid a session record names, an ACC runtime lease and a pin stop holding when their process is
  a zombie; runtime admission does not run the check. The pending generation's refresh removes
  zombie bindings and leases. The Codex service host reads a `<defunct>` daemon as dead. Doctor
  does not report a failed or cancelled job whose target is the active release with nothing
  pending.

## Upgrade from the published 0.9.1

The published `agents-can-communicate@0.9.1` was installed from npm into an isolated prefix,
with its own `HOME`, `ACC_DATA_HOME` and project, a `PATH` of the prefix, client stubs, node and
system directories, and a local registry that served this exact archive:

- **A live 0.9.1 process.** 0.9.1's own `acc-mcp` held contract 6, and `acc update` waited for
  it. After it exited, the next `acc status` activated 0.10.3. The store was on contract 7 within
  1.0 second, with event, journal, message and receipt bytes unchanged, and 0.10.3 answered the
  open question on it. The installed generation matched the archive file for file, and the Codex
  `config.toml` was unchanged. 0.9.1 code refused the migrated store with exit 4.
- **Stale bindings.** Two bindings without a pid for sessions with no record: the 0.9.1 updater
  activated 0.10.3 after its refresh removed them, and the store moved to contract 7. With a
  third binding for a session that still heartbeats, that one stayed and kept 0.10.3 pending.
- **A reused pid.** A binding written two days earlier, whose pid now belonged to a `sleep`
  started at the time of the run: the 0.9.1 updater activated 0.10.3, the binding was removed,
  and the store moved to contract 7.
- **A zombie.** A binding written a second after its process started, whose process had exited
  under a parent that never collected it (`ps`: `ZN`, `<defunct>`): the 0.9.1 updater activated
  0.10.3 while the process was still a zombie, the binding was removed, and the store moved to
  contract 7. The published 0.10.2, in the same setup, stayed pending on that pid.
- **A pending 0.10.2.** With 0.9.1's `acc-mcp` holding contract 6, `acc update` staged the
  published 0.10.2. Offered 0.10.3, `acc update` (which runs the pending 0.10.2's code) staged
  0.10.3 in its place; no `--pin none` was needed. Once the server exited, 0.10.3 activated, and
  only its generation remained.

## Upgrade from the published 0.10.0, 0.10.1 and 0.10.2

Each was installed the same way, with its own `acc-mcp` running and holding contract 7; their
published sha256 matched the recorded `ed5c2d88…`, `b899b2ca…` and `6e3d6350…`. Each
`acc update` printed `Updated ACC to 0.10.3; integrations refreshed.` without waiting. The
installed generation matched the archive file for file, and the Codex `config.toml` was
unchanged.

## Mixed versions

The published 0.10.0, 0.10.1 and 0.10.2 code, each run from its own package through its
entrypoint, shared one store with the installed 0.10.3: a question each way, each found in the
other's inbox and answered, both reported `2 live`, and both doctors reported the store healthy.

## The maintainer's data home

Read-only, on the live runtime with 0.10.2 active: no native hold would block a contract-7
activation. The maintenance record from the 0.10.2 update is still `failed (processes_active)`
for 0.10.2. The installed 0.10.2 doctor reports it; this tree's diagnostic gives `ACC 0.10.2 is

## Real clients

On the maintainer's Mac (macOS arm64), the real-clients tests ran against the candidate commit's
packed tree, with an isolated home and a model stub on 127.0.0.1. Claude Code 2.1.292 and
Codex 0.160.1 attached through their own hooks, saw each other and carried a message into the
next turn, and an idle interactive Claude Code woke through its inbox. Both passed on the first
run. The real-clients CI job passed on `ubuntu-latest` and `windows-latest` on the final head of
#282.

## Limits

- The maintainer's own machine is updated after publication; that result is not part of this
  record.
- A machine with a pending 0.10.0 or 0.10.1 still needs `acc update --pin none` once: their
  updater runs the decision and does not replace a pending release.
- No zombie existed on a real machine during these checks; the zombie cases used a real zombie
  made for the test. Linux was exercised only through CI. Windows has no zombie state.
